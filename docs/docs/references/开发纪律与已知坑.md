# 04 · 开发纪律与已知坑

> 全部来自真实事故。**动手前扫一遍，能省半天。**
> 每条格式：现象 → 根因 → 正确做法。

## A. 工具链（PowerShell / 编辑器）

### A1 中文和引号在 `node -e` 里被吃掉
- 现象：`SyntaxError: Invalid or unexpected token`、`Expected ',', got '<eof>'`、中文变乱码
- 根因：PowerShell 先解析一次，`"`、`|`、`(` 都可能被 PS 吞掉
- 做法：**一律写 `.cjs` 文件再 `node xxx.cjs`**；临时验证用 `node --check`；不要用 `node -e "…中文…"`

### A2 `.ps1` 里写中文 → 满屏语法错误
- 现象：`字符串缺少终止符`、`表达式或语句中包含意外的标记`
- 根因：PowerShell 5.1 对无 BOM 的 UTF-8 按 ANSI 解码；同样地 `edit`/`write` 工具写文件**不带 BOM**
- 做法：改 `.ps1` 用 node 脚本写回 **`'\uFEFF' + 内容.replace(/\n/g,'\r\n')`**，改完用
  `[System.Management.Automation.Language.Parser]::ParseFile($f,[ref]$null,[ref]$err)` 校验

### A3 按命令行模糊匹配杀进程 → 把自己杀了
- 做法：`Get-CimInstance Win32_Process | ? { $_.CommandLine -like '*xxx*' -and $_.ProcessId -ne $PID }`，**永远加 `-ne $PID`**

## B. erp/server.js（单文件后端）

### B1 新接口插得太靠前 → 请求挂死
- 现象：请求一直不返回（客户端超时）；`<data>\crash.log` 里有
  `ReferenceError: Cannot access 'send' before initialization`
- 根因：`send` 是在 `req.on('end', async () => { … })` 内部定义的；路由必须写在那之后
- 做法：新路由插在 **`const send = (code, data) => {…};` 之后**（或插在 `return send(404…)` 之前）

### B2 改了后端但接口 404
- 根因：没有重启 ERP（进程里跑的是旧代码）
- 做法：`node --check server.js` → `node _dev-tools\_erp_restart.cjs`（杀 3088 + 重拉 + 等 health）
- 注意：**采集正在跑时不要重启**（会中断采集 worker）

### B3 名字陷阱
- `DATA` 是数据目录变量（不是 `DATA_DIR`，后者会 `ReferenceError` 并让 ERP 崩）
- `/api/claims`（GET/POST）是**草稿箱**；跨店台账是 `/api/claims/*`
- `products` 数组里图片字段是 `mainImage`，落到前端 JSON 时也叫 `mainImage`（`image` 是 undefined）

### B4 时区
- `now()` 返回 **UTC**；`Date.parse('2026-10-24 15:21:27')` 按**本地**解析 → 差 8 小时
- 做法：`Date.parse(s.replace(' ','T') + 'Z')`

### B5 清库类接口（**血泪**）
- 事故：`POST /api/listing/records/clear {confirm:'NO'}` 把 **214 条上架记录清空了**（当时接口既不校验 confirm、也不限本机）
- 现状：已加 ① 仅本机 ② 必须 `{confirm:"CLEAR"}`
- 恢复手段：`<data>\backups\listing-records.json.<时间戳>.bak`（`save()` 落盘前会自动备份）
- 纪律：**动任何 delete/clear 前先确认 backups 里有当次快照**

### B6 索引与缓存
- 台账判决用内存索引 `claimIdx`：**peer 数据变更（import / delete / 启动加载）后必须 `claimIdxRebuild()`**
  - 症状：同步来的凭证在库里，却拦不住（或断开后还在拦）
- 启动顺序坑：`claimIdxRebuild()` 在台账引擎末尾调用时，`peerData` 还没加载 → 索引只有本地。**peers 引擎加载完要再 rebuild 一次**

## C. ifast 相关（bridge.js）

### C1 请求不带头 → 404 HTML 页
- 根因：ifast 用 `X-Requested-With: XMLHttpRequest` 区分 AJAX 与页面请求
- 做法：所有 ifast 请求都带这个头（`IFAPI.XRW`）

### C2 `code` 是空串不是 0
- `item_list.json` 返回 `{"code":"","count":2220,"data":[…]}` → 只按 `code===0` 判成功会误报"登录过期"
- 做法：`ok = (code === 0 || code === '' || code == null) && data`

### C3 页面显示 191 条 ≠ 只有 191 条
- 根因：ifast 页面默认筛选 **`minCreateTime=7`（最近 7 天）**
- 实测：`minCreateTime=7` → 191；不带 → **2220**；按站点求和 = 总数
- 做法：同步接口**不要带** `minCreateTime`；分页 `limit=100`，`while (got < total)` 自适应

### C4 `itemStatus` / `onOff` 别乱猜
- `itemStatus`：`0 正常 / 20 待获取 / 30 ASIN异常 / 40 异常`（页面 DOM 实测）
- `onOff` 恒为 0；**判断"有没有上架"只看"在 ifast 列表里存在"**

### C5 回退纪律（防重复上架）
- 只要 `POST item_add/product_add/item_edit` 已发出，**无论超时/非 0/看不懂，都不得重试或用 DOM 流程再提交一次**
- 只能：回读 ifast 判定"其实成功 / 早就存在 / 确实没成功（可安全重传）/ 未确认"

### C6 已存在的品不要硬当新增
- 同账号同站点 `item_add` 必被拒（`code=500 站点已经存在此ASIN`）
- 正确：先 `listingOf` 回读 → 存在则走 `item_edit`（更新价格/承受价/库存/跟卖组）

## D. 扩展（MV3）

### D1 内容脚本不能直连 ERP
- 现象：`fetch('http://127.0.0.1:3088/...')` 失败（CORS/权限）
- 做法：内容脚本一律 `chrome.runtime.sendMessage`，由 background 发请求

### D2 跨设备访问内网 IP 需要权限
- `manifest.host_permissions` 只有 `127.0.0.1` 时，别的电脑填 `http://192.168.x.x:3090` 会被拦
- 现状：已加 **`http://*/*`**（跨机取数必需）

### D3 重载了扩展但页面还在跑旧脚本
- 现象：改了 bridge.js 没生效 / `Receiving end does not exist` / `Extension context invalidated`
- 做法：`chrome.runtime.reload()` 或 `edge://extensions` 重载后，**必须 F5 刷新 ifast / Amazon 页**

### D4 消息没回执 → 控制台刷 `Unchecked runtime.lastError`
- 做法：回调里必须读 `chrome.runtime.lastError`；或用 `try/catch` 包 `sendMessage`

### D5 面板/弹窗 DOM id 是契约
- `#zying-bridge-panel` `#zying-br-*` `#zyv-port-*` `#zyv-peer-*` `#zyv-claim-*` 都被验收脚本依赖
- **改 id 会让 `_dev-tools` 里的脚本全红**；要改就同步改脚本

### D6 消息锁把报错吃掉了
- 现象：点了按钮"没反应"，报错不显示
- 根因：`setMsgLock(t, ok, ms)` 在 ms 内阻止 `setMsg` 上屏；上一步的"成功"会挡住这一步的"失败"
- 做法：动作开始先 `zvMsgUnlock()`；失败提示用 `setMsgLock(…, false, 15000)`

### D7 "先重绘，再做装饰性动作"
- 事故：创建端口成功后调用 `say()` 抛错 → 后面的 `zvPortsRefresh()` 整段被跳过 → 用户看到"点了没反应"
- 做法：**UI 更新排第一**，提示/复制/日志各自 `try/catch`，最后再 `setTimeout` 兜底刷新一次

### D8 表格被撑宽 / 行高爆炸
- 用 `table-layout:fixed` + **百分比列宽**；`box-sizing:border-box` 必须显式写
- 一组按钮挤不下就 `display:flex;flex-wrap:wrap;gap:2px`，并清掉子元素的默认外边距（excel/页面的 `tr>*` 都可能带 margin）

## E. 采集浏览器（反复死亡的老问题）

### E1 症状与事实
- 现象：任务 paused + `connect ECONNREFUSED 127.0.0.1:9222`，界面表现"链接 N 条 → 卖家 0 个"
- 已排除：不是采集逻辑问题；`exit_type=Crashed`、无崩溃转储、事件日志无 msedge 错误
- 现状：**ERP 采集接口会按需自动拉起采集浏览器**（`ensureCollectBrowser`），不再依赖用户先开
- 看门狗 `_keep_collect_browser.ps1` 默认跑在 `-NoAutoLaunch`（只监控不启动，避免莫名弹窗）

### E2 启动采集浏览器的正确姿势
```powershell
msedge.exe --remote-debugging-port=9222 --user-data-dir="%LOCALAPPDATA%\Microsoft\Edge\User" `
  --no-first-run --no-default-browser-check `
  --disable-features=DisableLoadExtensionCommandLineSwitch `
  --load-extension=D:\智赢erp\zying-collector https://www.ifast.top/amazon/selling/item/item_list.html
```
用 **PowerShell Start-Process** 拉起（不要用 ERP 的 `child_process.spawn`，会跟着 ERP 一起被杀）。

### E3 ★ 2026-10-31：9222 起不来的真凶是「日常 Edge 占着同一个 profile」
报障原文：`失败 4 条: https://www.amazon.es/s?me=... → 采集失败: connect ECONNREFUSED 127.0.0.1:9222`（知产查重·多链接）。

三个叠加的 bug（都已修，改的是 `erp/server.js`）：
1. **`/api/ip/list-check` 没有「采集前确保 CDP」这一步** —— 只有 `/api/collect/*` 那个守卫里有
   `ensureCollectBrowser`。所以浏览器没开时，列表查重在 **2 秒内**把每条链接都判成失败，
   任务 `productCount=0 brandCount=0`，界面上只看到"失败 4 条"。
   → 修法：`/api/ip/list-check` 动手前同样 `await ensureCollectBrowser('/api/ip/list-check')`，
   起不来就返回 503（带可操作提示）；逐条错误里把 ECONNREFUSED 翻译成"采集浏览器没开"。
2. **自动拉起写死用手日常 Edge 的默认 profile**（`%LOCALAPPDATA%\Microsoft\Edge\User`）。
   日常 Edge 正在跑时，再起一个带 `--remote-debugging-port` 的 msedge 只会被**转交给已有实例**，
   端口永远不监听 → 自动拉起"成功执行但永远不会就绪"。
   → 修法：`collectProfileCandidates()` 候选表 + `profileInUse()` 占用探测，跳过被占用的 profile，
   依次试 ① 环境变量 ② 默认 profile（带官方智赢插件）③ `D:\智赢erp\edge-debug-profile`
   ④ `%LOCALAPPDATA%\ZYingCollectProfile`；失败时把每个候选的失败原因带回去。
3. **列表采集"死等 6.5s 就解析"→ 静默丢数据**。`cdpListBrands` 原来 navigate 后固定等 6.5s
   （点完 Cookie 墙等 7s）就开始解析；实测 amazon.es / amazon.fr 的 `/s?me=` 打开后 Amazon 还要再走
   一次 glow 地址刷新（`&refresh=1&ref=glow_cls`），解析那一刻 DOM 里一张卡片都没有 →
   被写成「第 1 页没有新商品, 停止翻页」，**0 商品 0 品牌但状态算成功**。
   → 修法：**渲染闸门** `waitCards(ms)`，等到「有卡片」或「页面明确说无结果」才算渲染完（≤25s），
   两者都没等到就重载一次再等（18s）；0 商品时区分三种情况（跳回首页 / 明确无结果 / 压根没渲染出来）。
   ⚠ 只修浏览器没用：这一条会让「浏览器明明开好了」也照样丢数据。

排障口诀：`Get-NetTCPConnection -LocalPort 9222` 没监听 → 先看 `Get-CimInstance Win32_Process`
里有没有带 `--remote-debugging-port` 的 msedge，再确认它用的 `--user-data-dir` 是不是正被日常 Edge 占着。

## G. 授权（换机器才会遇到）

- 授权 = Ed25519 离线授权，指纹 = `sha256(hostname|platform|arch|cpu0|mac)[:16]`（**与数据目录无关**）
- 第二个 ERP 实例（如虚拟设备）报 `no-license` → 把 `data\license.key` 复制到新数据目录即可（同一台机器指纹相同）
- `erp/license.config.json` 的 `enforce:true` 时，无有效 key → 所有 `/api/*` 403

## H. 上架价格链：出售价的「±」在多选/整族上传时被静默丢掉（2026-11-03 修）

**现象**：Amazon 页面板里「出售价」右边的「±」框填了数字，上架记录/ifast 里价格没加减。单个上传看着正常，多选上传就丢。

**数据链（谁读谁）**：
```
面板输入 ±  → content.js 事件委托 → zvW(x).padj = n ; zvSave()
zvPayload(x)
  ├─ initPrice      = zvPriceFinal(x,d) = 基准(手填 init / 页面价) + padj   ← 单个上传用这个 ✓
  └─ variantItems[] = zvRowItem(...)    ← 多选/整族用这个（每变体一项）
        ↑ 原实现只取 d.init / 页面价，【没有 + padj】                      ← BUG 就在这
POST /api/listing/upload → ERP fill{initPrice, variantItems, ...}（服务端只存不重算）
bridge.js 上架
  ├─ API 多选通道  L2099 initPrice = variantItems[i].initPrice   ← 不回落到任务顶层值，所以传的是基准价
  ├─ API 单条通道  L2118 price     = f.initPrice                 ← 带 ±
  └─ DOM 通道      L1325/L1394 同上（multi 用 variantItems，single 用 f.initPrice）
```

**定位方法（可复用）**：扫 `data/listing-records.json`，比较 `fill.initPrice`（最终价）与 `fill.initHand`（手填价）——
不等于就说明 ± 生效过；再看同一条的 `fill.variantItems[].initPrice`，如果**逐变体价 == 手填价**而顶层价 != 手填价，
就是「顶层对、逐变体错」的典型指纹（实例：2026-10-30 13:19 `B0H9XGW9D6` 手填 205、顶层 215、variantItems 全 205）。

**修法**：`content.js` 的 `zvRowItem()` 改用 `zvPriceFinal(it, d)`（与单条路径同口径）；
`erp/server.js` 的 `fill` 增加 `initBase` / `initAdjRow` 落库（原来只有承受价有 `bearBase`/`bearAdjRow`，出售价没留痕，
出问题时只能靠猜）。回归脚本 `_dev-tools/_test_padj_fix.cjs`（用 content.js 真实函数体做离线断言，含 3 条对齐真实历史记录的用例）。

**教训**：同一个业务值存在两条计算路径（单条 vs 每变体）时，抽一个 `zvXxxFinal()` 出来两边共用；只要有一处"手算基准价"，
迟早分叉。落库时把**输入**（基准/加减量）和**输出**（最终价）都存下来，否则无法事后核对。

## I. 「已上架」判定 + 商品管理筛选 + 采集数据锁（2026-11-03）

### I1 为什么会有这一节
`搞薯条-开发记录-20261031.md` 里 §3.3/§3.13 那批改动（`listedAsinSet`、`apply-stores`、`archive-sync`、`listed` 筛选、未上架标签）
在当时的多次插入/回滚中**整体被回滚掉了**（文档 §7.1 有记录），所以 2026-11-03 重新落地并做了加固。
核对方法：`grep listedAsinSet erp/server.js` —— 有就是新代码，没有就是被回滚的老代码。

### I2 「已上架」唯一判据（数据语义红线，别再用 claims 判定）
```js
listedAsinSet()   // selectionArchive.items 里 src==='ifast' 且 status!=='removed' 的 ASIN
                  // ∪ products[].ifastListed===true；缓存 60s，变更后调 invalidateListedCache()
listedShopsOf(asin) // 该 ASIN 在 ifast 归档里的店铺名列表（界面标签直接用它）
```
- `/api/claims/mark-batch` **先按 `listedAsinSet()` 过滤**，再用归档覆盖 `stores/items`（旧台账里 storeName 空的 1.8 万条不再误标）
- 反例（验收用）：`B07SV6HT1M` 在 ifast 里 0 条 → 必须**不出现**在 marks 里；`B0BMKM83SC` 只显示「全天跟卖」

### I3 ifast → 商品库/归档 三件套（改完标签必须先跑一遍）
| 接口 | 作用 | 实测 |
|---|---|---|
| `POST /api/ifast/archive-sync` | ifast 商品全量重刷归档（含 removed 标记、批次 keys、syncLog、旧 `店铺|asin@site` 键归一） | ifast 2230 → 归档 2481（删掉 2230 条重复旧键） |

### I4 三个筛选（后端 + 界面都要在）
- `filter={"listed":"1"|"0"}`：命中/未命中 `listedAsinSet()`；**采集过滤**同名字段语义为"采集时排除已上架"
- `filter={"shop":"全天跟卖"}`：按归档店铺名筛
- `filter={"conflict":"1"}`：只看采集数据冲突（见 I5）
- 界面：`lib/client.js` 的 `NF()` 增加 `listed/shop/conflict`，筛选面板加三行，卡片加「未上架」灰标 + 「数据冲突」橙标

### I5 采集数据锁（用户口径：允许多网页并发，入库要判重）
1. **单飞**：`/api/collect/*` 与 `/api/ip/list-check` 互斥（两边都在驱动同一个 CDP 浏览器），任一在跑，另一个直接 409
2. **入库判重**：`ingestLinksProducts()` 按 `asin@site` 建索引 → 逐条算**内容指纹**（title/brand/price/rating/reviews/mainImage/fulfill/listedAt）
   - 指纹一致 → 只留一条（`same++`，不重复写库）
   - 指纹不一致 → **两份都留**：字段级合并非空值 + 新版本压进 `altVersions[]`（最多 5 份）+ `conflict=true`
     （products 主键仍是 `asin@site`，双版本放 altVersions，不破坏主键唯一性；界面可按「数据冲突」筛）
   - 合并时写 `priceHistory`（最多 30 条）
   - 旧实现只按 `asin` 判重并直接 skipped 丢弃 → 同 ASIN 跨站点被误杀、更新数据永远进不来
3. **落盘**：`writeFileNow()` 已是 tmp 写 + rename 原子替换 + 备份轮转（改这块前先看它，不要再加第二套写盘）

### I6 一条命令验收

### J5 UKIPO 逆向接入（2026-11-03，推翻 J3 的「接不上」结论）

**数据卡在哪（Edge/CDP 三级定位）**：

1. 裸 HTTP：403 + Service Captcha（Cloudflare 边缘；只给 __cf_bm，没有 cf_clearance）
2. 真实浏览器：首页弹 Cloudflare Turnstile，但 3~13 秒会自动过，种下 cf_clearance
3. 过了之后：不是登录墙（搜索完全公开），也不是没有 API —— 搜索是标准 Spring MVC 表单流：
   - GET /ipo-tmtext → 拿 csrfToken（隐藏域）
   - POST /ipo-tmtext（form-urlencoded：csrfToken / sectionIndex=0 / searchType=WORD / wordSearchType=EXACT / wordSearchPhrase=词 / wordSearchMatchType=ALLWORDS / filedFrom / filedTo / legalStatus=ALLEGALSTATUSES / pageSize=50）→ 303 → /ipo-tmtext/page/Results
   - GET /ipo-tmtext/page/Results?page=1 → 服务端渲染结果（纹号 / Status / Mark text / File date / Classes）

四个必踩的坑（都实测过）：

| 坑 | 现象 | 正确做法 |
|---|---|---|
| 只 GET 带 ?wordSearchPhrase= | found 0 marks（条件不在 URL 里） | 必须先 POST 建会话查询条件，再 GET 结果页 |
| cf_clearance 与 UA 绑定 | 浏览器里好好的，Node 一发就回挑战页 | HTTP 请求必须沿用浏览器真实 UA（Edg/156…），引导时一并取回 |
| 命中 >1000 条 | 400「Refine your criteria, there are more than 1,000 results」 | 默认 wordSearchType=EXACT；超限时给友好提示，不重试 |
| filedTo 填未来日期 | 400（页面不报错、只回壳） | filedTo 用当天（day/month/year 分三个字段） |

**实现**：

- `erp/server.js` → `ipCheck.setUkipoBootstrap(fn)`：`cdpCreateTab` 开 `/ipo-tmtext`，轮询 `Network.getCookies` 直到有 `cf_clearance`（≤45s），**把浏览器 UA 一起返回**
- `erp/ip-check.js` → `searchUkipo()`：会话存 `~/.zying-erp/data/ukipo-session.json`（20 分钟 TTL）；每次检索 = GET(csrf) → POST(303 跟到结果页) → `parseUkipoResults()`；403/captcha 自动重新引导一次

### J8 「❓ 无法判定」的成因与治理（2026-11-03）

用户报障：知产查重里 `smyzj` 英国站显示「❓ 无法判定 · 商品 1 个」。

**定位结论：既不是缺数据，也不是没查到，而是查询那一刻所有数据源都失败了。**

- 结论文案本身就是 `⚠️ 无法判定 —— N 个数据源全部查询失败（detail）`（`ip-check.js` 聚合逻辑：全部失败 → unknown）
- 商品库里没有 `ipCheck.term=smyzj` 的记录 → 那次是页面上的批量结果（内存态、未落库），所以事后只能靠重查

- 当时为何全失败：UKIPO 正处于 Cloudflare 人工验证状态（测试期触发），叠加 WIPO 会话抖动 → 多个源同时 failed

**治理（已实施）**：`ip-check.js` 的 `search()` 里对「失败且 ready」的源自动重试一次（间隔 900ms）：
重试成功 → 采用新结果，不再判 unknown；仍失败 → 错误信息追加「（已重试仍失败）」，界面可区分真查不了与一时没查成。

桩测验证（`_dev-tools/_test_ipretry_stub.cjs`）：

```
第 1 次抛错 / 第 2 次成功 → 调用 2 次，ok=true，level=none（不再 unknown）
两次都抛错              → 调用 2 次，level=unknown，err=…（已重试仍失败）
```

**处置建议**：看到 unknown 先看是哪个源失败（单源多为会话/风控，多源同时失败多为网络或同时被风控）；重查一次即可 —— 失败结果不进 7 天缓存，所以重查一定是真请求。

### J12 插件打开页面：必须走本地浏览器，不走 ego（2026-11-04）

用户口径：插件/其它入口打开的页面用**本地浏览器**；ego 只在做开发/浏览器自动化时由 AI 自己开。

**发现**：Windows `UserChoice(http/https)` 已被 **ego lite** 抢成默认（`egoliteHTM`）。
而 `/api/open` 原来用 `cmd /c start "" <url>` 跟随系统默认 → 插件点「打开商品页」会开 ego。

**修法（server.js）**：

- 新增 `localBrowserExe()`：按 `ZYING_LOCAL_BROWSER` 环境变量 > Edge(Program Files (x86)/Program Files) > Chrome 顺序探测；
- 新增 `spawnLocalBrowser(url)`：**以 argv 直接传 URL** 拉起本地浏览器（不经 cmd.exe，URL 的 `&` 不会被截断）；
- `/api/open` 先走本地浏览器，返回 `via: 'local:msedge.exe'`；找不到本地浏览器才回退原来的 `cmd start`。
- 采集浏览器本来就是 `msedge.exe`（`ensureCollectBrowser`），不受影响。

**验收**：`GET /api/open?url=https://example.com/?a=1&b=2` → `via=local:msedge.exe`，调用前后 ego 进程数 0→0（没有落到 ego）。

**系统默认浏览器本身**仍是 ego（`egoliteHTM`）：要恢复成 Edge 需在「设置 → 应用 → 默认应用」里改（用户点击一次），

### J44 「多链接采集失败 · proxy-unavailable」根因与修复（2026-11-18）

**现象**：面板点「多链接采集」→ ❌ 多链接采集失败 / proxy-unavailable；ERP 侧查不到任何任务/数据。

**链路追踪**：
```
面板(client.js) → POST /api/zying-proxy（DSH 同源代理，dsh-app:// 不能直连 3088）
              → host 代理 handler fetch http://127.0.0.1:3088/api/collect/shop-links
              → hcCollectMode('links') 同步跑完才返回（多链接常有 60~120s+）
```
client.js 只有 `/api/zying-proxy` 成功时才用代理；失败且页面是 dsh-app://（非 http/https）→ 直接返回 `proxy-unavailable`。

**根因**：HTTP 通道的多链接采集是**同步长请求**（一次能跑 1~3 分钟），DSH 代理/客户端这一跳先超时断开 →
客户端拿不到响应 → 报 proxy-unavailable。采集请求可能已经在后端跑起来了，但用户看到的是失败，任务卡里也没有记录（旧版 HTTP 不建 job）。

**修复**：
1. 多链接 HTTP 分支改**后台异步**：立即返回 `{ok,started,links}`（实测 0.03s），后台继续跑，写 `bumpCollectProgress` + `links-result`；
   失败时写 `taskStatus:'failed'` + `errors[]`，不再让用户看到笼统的 proxy-unavailable；
2. **每条链接按自己的域名算站点**（原来整批用第一个链接的 site：UK 链接会被存成 FR）；
   切换前按站点调 `localeFixHttp(linkSite)`，分站点入库；
3. `links-result` 的 shops 改成**按站点分组**（HTTP 直连 FR / UK / DE 各一行）。

**端到端验证**：
```
提交(FR+UK+DE 三链接) → 0.03s 返回 started
progress: 启动 → 取链接 2/2（list）→ 完成
links-result: shops=[(HTTP 直连 FR) 4, (HTTP 直连 UK) 4, (HTTP 直连 DE) 4]，totalAdded=11 updated=1 elapsed=34s
并发保护: 运行中再提交 → HTTP 409「已有采集正在运行」
```

**遗留风险**：跟卖 / 品牌 / 批量 三个 HTTP 模式仍是同步返回，超大任务同样可能超时；建议这些模式用较小 maxItems 或 transport:'cdp'。

- 变体表格的 BG 列：`GET /api/bg/lookup?site=&asins=` 一次批量（最多 60 个 ASIN）**只读商品库/缓存**，不发实时探测 → 毫秒级；
- zy-list.js 无 BG 调用；插件没有对多个 ASIN 循环实时探测的实现。

结论：插件内 = 单商品一次请求（内部店铺并行），**不存在串行排队**；变体批量 BG 仅读库。

### J78 澄清：两个插件里的 BG 是「实时请求」还是「查库」

**先分清两个库**：
- 本地商品库：`data/products.json`（我们采集/检测后存下来的快照）；
- 智赢数据接口：智赢服务器的 HTTP API（按 ASIN/站点实时查，BG 需按店铺账号查）。

**BG 没有“按 ASIN 从智赢库直接批量读”的接口**，只有按店铺账号实时探测；存下来的只是快照。

| 端 | 操作 | 数据来源 |
|---|---|---|
| 浏览器插件 | 面板当前商品 BG | **实时请求** `/api/bg/probe-multi` |
| 浏览器插件 | 变体表格 BG 列 | **本地库** `/api/bg/lookup`（最多 60 ASIN） |
| 搞薯条插件 | 商品卡/筛选里的 BG | **本地库**（bgStatus/bgByAccount 快照） |
| 搞薯条插件 | 点卡片 BG 标签 | **实时请求** -> 写库 |
| 搞薯条插件 | 「📥 获取BG (全部筛选)」/详情页按钮 | **实时请求**（逐商品 x 多店铺）-> 写库 |

结论：两端都是“实时请求 + 本地快照”混合，差别只在触发时机与批量对象。
